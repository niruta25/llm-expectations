llm-expectations architecture overview

A quality job for
model output

It runs after your inference pipeline, reads the rows it produced, and writes findings you can load and query. No service, no dashboard, no orchestration of its own — a CLI that reads files and writes files.

01 The job

Where it sits

Your pipeline classifies or summarises a corpus. This reads what it wrote and answers three questions: which rows should a human open, how good is the set overall, and which numbers are not trustworthy enough to report. 

  your pipeline                       llm-expectations
  ─────────────                         ────────────────

  items ──► model ──► outputs.jsonl ──►  free checks
                                         judges          ──►  findings.jsonl
                                         metrics              verdicts.jsonl
                                                              metrics.json
                                                              report.md
                                                                   │
                                                                   ▼
                                                         warehouse · BI · alerts

           observe-only. it never calls your extractor
           and never writes to your tables.
Fig 1 — a downstream quality job, not a wrapper around your inference

What it is checking

Not values copied out of a document — those you verify with a string search, and other tools already do. This covers output that is a judgement about the document, where nothing in the source can confirm it.

KindExampleIn the source?How it gets checked
assigned jtbd: billing.payment_failed no Compare against a right answer — human, or a judge standing in for one
free_text summary: "card declined at renewal" no No single right answer exists. Hunt for specific defects
copied total: $2,450.00 yes Search the text. Free, and it gates everything downstream — v1

The cost consequence, up front

For copied fields the free check is predictive, so you only pay a judge for suspicious rows. For assigned fields the free checks catch format problems, not wrongness — a well-formed label that is simply the wrong one passes all of them. So one judge sees every row. That is the whole bill, and the design says so rather than burying it.

Formats

JSONL by default because it streams — you can point it at 500,000 rows without loading them. CSV, Parquet, and pandas or polars frames go through swappable readers. Warehouse sources are v1; files cover the first year.

Credentials

judges.yml references API keys by environment-variable name, never value, so the config is safe to commit next to your DAGs.

03 Metrics

What gets computed, and what it costs

Most of it needs no human labels. What a field gets depends on its mode, decided per field and recomputed every run.

modeYou supplyYou get
0 nothing label validity · distribution and collapse · drift vs last run · abstention rate · judge approval rates · relative leniency · cross-field consistency · fuzzy label pairs · triage ranking
1 ~100 labelled + accuracy · macro F1 · per-label precision and recall · confusion matrix · tree buckets · judge direction · confidence calibration · the operating-point table
2 ~100 double-labelled + whether the taxonomy is actually crisp — and everything above becomes trustworthy

The headline is an operating point, not an AUC

"AUC 0.84" cannot go into a capacity plan. This can: 

  review budget       errors found      wasted review
     500  (1%)              18%               2%
   2,500  (5%)              54%              11%
   5,000 (10%)              71%              29%
Fig 2 — the deliverable, for a 50,000-row corpus

Cost model

ComponentcallsScope
Free checks0every row, every run
Triage judge1 × rowsevery row — this is the bill
Panel3 × sample~300 rows, configurable — a rounding error
Claim check (free text)~0.2 × rowsflagged rows plus an audit stratum

Every output row carries cost_usd, so spend is queryable by check, field, judge and run. A budget cap marks rows ○ unscored rather than silently passing them.

Three statuses, not two

✓

pass

Checked, and fine.

✗

fail

Checked, and wrong. Evidence attached.

○

unscored

Not sampled · budget spent · judge returned nothing · check does not apply. skip_reason says which. Never becomes a pass.

Collapse this to a boolean and a run that quietly stopped checking reports green. Budget exhaustion is the common case, and it is exactly when you least want a clean dashboard.

05 Consuming it

Load the files and query them

There is no dashboard and there will not be one — the output is shaped to feed whatever you already run. index.jsonl is the run-level fact table; findings and verdicts are the detail.

the four views worth building first
-- 1. coverage rot: what are we quietly not checking?
SELECT check, skip_reason, count(*) AS n
FROM findings WHERE status = 'unscored'
GROUP BY 1, 2 ORDER BY n DESC;

-- 2. the grain gap: field pass rate always flatters item pass rate
SELECT grain, avg(CASE WHEN status = 'pass' THEN 1.0 ELSE 0 END)
FROM findings WHERE status <> 'unscored' GROUP BY 1;

-- 3. judge health over time — catches a grader going stale
SELECT r.started_at, v.judge,
       avg(CASE WHEN v.verdict = 'true' THEN 1.0 ELSE 0 END) AS approval_rate
FROM verdicts v JOIN runs r USING (run_id)
GROUP BY 1, 2 ORDER BY 1;

-- 4. undefended thresholds: numbers somebody typed
SELECT check, count(*)
FROM findings WHERE threshold_from = 'default' AND status = 'fail'
GROUP BY 1;

Alert on the derived views, not on failure counts

A rising share of unscored means you are checking less than you think. A widening grain gap means errors are spreading across fields. A judge's approval rate drifting means your measuring instrument moved, not your quality.

orchestration — it is just a CLI task
llm-expectations plan     run.yml
# cost estimate, issues no calls

llm-expectations run      run.yml
# collect + analyse

llm-expectations analyse  out/<run>/
# re-analyse from cache, free

llm-expectations compare  out/a out/b
llm-expectations check    taxonomy.yml

Reproducibility

Same inputs plus the same cache produce the same output. analyse is deterministic and issues zero model calls.

Lineage

Every run stamps the model, prompt version and taxonomy version. Two runs whose stamps differ are not comparable, and the tool refuses to compare them rather than drawing a trend line across a definition change.

Incremental cost

The verdict cache is keyed on judge, model, prompt hash and row content, so re-running a grown corpus pays only for the new rows. 

   COLLECT  ──► verdicts.jsonl          costs money. run once.
                        │
                        ▼
   ANALYSE  ◄────────┘                  free. run a hundred times.

   cache key = (judge, model, prompt hash, item, field, output value)
Fig 4 — the only expensive operation is isolated behind a file

Change a threshold, add a check, fix a reporting bug, try a different target — re-run against the cache and pay nothing. Cheap reporting code that only ever runs after an expensive collection is its own failure mode; this removes it.

the entire seam

    name        # assigned | free_text

every check, one signature
check(items, outputs, ctx)
    -> list[Finding]

# the runner walks a list.

Checks come in three grains

field — one row, one column. item — one row, several columns, which is where cross-field consistency lives ("does the summary agree with the label?"). corpus — the whole batch: distribution, drift, boilerplate.

Labels arrive on a path the judge cannot see

A judge graded against the answer key produces beautiful, worthless numbers. Prevented by the function signature, not by a convention someone has to remember. 

   Item   ──┐
            ├──►  judge  ──►  Verdict  ──►  Finding
   Output ──┘

   Label  ────────────────────────────►  metrics only

          the judge-calling code does not accept labels.

07 Judges

Two jobs, wired separately

A panel and a single judge answer different questions and cost different amounts. Conflating them is how teams end up paying triple for one opinion. 

  PANEL    3 judges × ~300 rows           ~900 calls
           ├─ quality estimate, with an interval
           ├─ which label pairs the judges keep splitting on
           └─ side-by-side health check of the judges

  TRIAGE   1 judge × every row            50,000 calls
           └─ risk = 1 − mean confidence across the row's fields
              sort desc, review until the budget runs out
Fig 7 — scope and cost, for a 50,000-row corpus

Screening, free and always on

A judge approving 94% of everything passes every format and parse check ever written. The approval-rate table is the only thing that catches it, and it needs no labels.

Relative leniency is free too: when two judges disagree, note who approved. 188 to 14 in one direction tells you which one is the pushover.

per-judge health
judge     approves  unsure  unread.
judge-a      71%      4%     0.3%
judge-b      58%      2%     0.7%
judge-c      94%      0%     0.0%  ⚠
Deliberately not doingWhy
Routing disagreements to review Judge disagreement does not rank errors — it lands close to chance. On contested labels it actively selects the rows nobody can resolve.
Auto-approving on unanimity Judges agree on the large majority of rows and are wrong about a meaningful share of what they agree on. Consensus is not proof.
A single blended panel score Averaging a 2–1 split throws away the only interesting part. The split and the dissenting reason are both written out.

08 Guardrails

Checks on the measurement, not the data

Each catches a failure that otherwise produces a confident, plausible, wrong number. They run first and cost nothing. Every threshold is a default you can change — except the last one.

GuardraildefaultCatches
Judge approval rate15–85% A rubber-stamp judge. Approving 99% passes every other check ever written.
Unreadable replies< 2% Counted, never defaulted. A fallback verdict is uncorrelated by construction and silently shifts every agreement number.
Which rows failedreported Empty replies cluster on long, hard rows — your worst cases going unjudged.
Minority class floor30 and 5% An AUC ranking three negatives looks fine and has a tight-looking interval.
Sample floor for rankingn ≥ 200 Below it the interval spans useless to excellent. That is not a weak result, it is no result.
Taxonomy hashalways on Someone tightening a definition without bumping the version, and a month of results quietly ceasing to be comparable.
Label-leak assertionnot tunable A triage signal that saw the answer. The one setting you cannot turn off, because it is a bug check and not a threshold.

They suppress numbers, not the run

A guardrail firing removes the specific figures it invalidates and prints why. Everything else still lands. 

  ┌ WHAT THIS RUN CANNOT TELL YOU ───────────────────────┐
  │  ✗ triage AUC for `summary`                           │
  │      12 rows in the minority class, need 30           │
  │                                                       │
  │  ✗ judge-c's contribution to panel agreement          │
  │      approved 97% of rows — excluded                  │
  │                                                       │
  │  ✗ drift vs the previous run                          │
  │      taxonomy moved v4 → v5, no mapping supplied      │
  └───────────────────────────────────────────────────────┘
Fig 8 — every report carries this block, even when empty

Gate 1

Can the measurement be trusted?

The guardrails above. If they fail, everything downstream is decoration.

Gate 2

Is the judge better than guessing?

Scored against random, always-approve, majority-label and item length — same target, printed side by side, always.

Then

Quality numbers

Only once both gates pass does anything else get reported.
