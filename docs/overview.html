llm-expectations architecture overview

Checking output
that isn't in the input

Extraction QA rests on one free check: is this value present in the source text? For a category label or a written summary, it isn't — and never was. Everything here follows from that.

The founding constraint

Three kinds of field, and only one is groundable

KindExampleIn the source?How you check it
copied total: $2,450.00 yes Search the text. Free, and strong enough to gate everything downstream.
assigned jtbd: billing.payment_failed no Compare against a right answer — human, or a judge standing in for one.
free_text summary: "card declined at renewal" no No single right answer exists. Hunt for specific defects instead.

v0 builds assigned and free_text. copied is v1 — the seam is in place, and adding it should touch no engine code.

The consequence that costs money

For copied fields the free check is predictive, so you only pay a judge for the suspicious ones. For assigned fields the free checks catch format problems, not wrongness — a well-formed label that is simply wrong passes all of them. So one judge has to see every item. That is the whole bill, and the design says so rather than hiding it.

Data model

Labels arrive on a separate path

A judge grading itself against the answer key is the easiest mistake in this whole space, and the hardest to spot afterwards — the numbers come out beautiful. So it's prevented by wiring, not by a convention someone has to remember. 

   Item   ──┐
            ├──►  judge  ──►  Verdict  ──►  Finding
   Output ──┘

   Label  ────────────────────────────►  metrics only

          the judge-calling code does not accept labels.
          it is not a rule. it is a function signature.
Fig 2 — no path from Label to a judge
TypeWhat it holds
ItemThe unit — a session, ticket, document
SchemaEach field and its kind
TaxonomyA versioned label tree, hashed and stamped into every run
OutputWhat the model produced for one item + field
LabelA human answer, with the annotator's id. Optional.
VerdictOne judge's call on one output, with a one-sentence reason
FindingA check result: pass / fail / unscored, with evidence

Result states

Unscored is a first-class answer

✓

pass

Checked, and fine.

✗

fail

Checked, and wrong. Evidence attached.

○

unscored

Not sampled · budget spent · judge returned nothing · check doesn't apply. Never converts to a pass.

Collapse this to a boolean and a run that quietly stopped checking reports green. Budget exhaustion is the common case, and it is exactly when you least want a clean dashboard.

Judges

Two jobs, wired separately

A panel and a single judge answer different questions and cost different amounts. Conflating them is how teams end up paying triple for one opinion. 

  PANEL    3 judges × ~300 items          ~900 calls
           ├─ quality estimate, with an interval
           ├─ which label pairs the judges keep splitting on
           └─ side-by-side health check of the judges

  TRIAGE   1 judge × every item           50,000 calls
           └─ risk = 1 − mean confidence across the item's fields
              sort desc, review down the list until budget runs out

           the panel is a rounding error.
           the triage judge is the entire bill.
Fig 3 — scope and cost, for a 50k-item corpus
one Verdict type, both kinds
Verdict:
  judge       "judge-b"
  item_id     "s-1042"
  field       "summary"
  verdict     True | False
              | cannot_decide
  confidence  0.0 – 1.0
  reason      one sentence
  detail      {} — claim lists etc

Why one shape matters

Because the shape is common, all of this works for both field kinds with no extra code: approval-rate screening, parse-failure tracking, panel voting and dissent, relative leniency, the triage risk score, verdict caching.

Give free text its own verdict type and every one of those gets written twice.

Deliberately not doingWhy
Routing disagreements to review Judge disagreement does not rank errors. It ranks close to chance, and on contested labels it actively selects the items nobody can resolve.
Auto-approving on unanimity Judges agree on the large majority of items and are wrong about a meaningful share of what they agree on. Consensus is not proof.
A single blended panel score Averaging a 2–1 split throws away the only interesting part. The split and the dissenting reason are both reported.

Guardrails

Checks on the measurement, not the data

Each one catches a failure that otherwise produces a confident, plausible, wrong number. They run first and cost nothing.

GuardraildefaultCatches
Judge approval rate 15–85% A rubber-stamp judge. Approving 99% passes every format and parse check ever written.
Unreadable replies < 2% Counted, never defaulted. A fallback verdict is uncorrelated by construction and silently shifts every agreement number.
Which items failed reported Empty replies cluster on long, hard items. Your worst cases going unjudged.
Minority class floor 30 and 5% An AUC that ranks three negatives looks fine and has a tight-looking interval.
Sample floor for ranking n ≥ 200 Below it the interval spans useless to excellent. That's not a weak result, it's no result.
Label-leak assertion always on A triage signal that saw the answer. Scores beautifully, worth nothing in production. The one setting you cannot turn off.
Taxonomy hash always on Someone tightening a definition without bumping the version, and a month of results quietly ceasing to be comparable.

They suppress numbers, not the run

A guardrail firing removes the specific figures it invalidates and prints why. You still get everything else. 

  ┌ WHAT THIS RUN CANNOT TELL YOU ───────────────────────┐
  │  ✗ triage AUC for `summary`                           │
  │      12 items in the minority class, need 30          │
  │                                                       │
  │  ✗ judge-c's contribution to panel agreement          │
  │      approved 97% of items — excluded                 │
  │                                                       │
  │  ✗ drift vs the previous run                          │
  │      taxonomy moved v4 → v5, no mapping supplied      │

Gates

Two questions before any quality number

Gate 1

Can the measurement be trusted?

The guardrails above. If they fail, everything downstream is decoration.

Gate 2

Is the judge better than guessing?

Scored against random, always-approve, majority-label and item length — on the same target, printed side by side, always.

Then

The operating point

Not an AUC. "Review 2,500 of 50,000 and you find 54% of the errors" is the number a capacity plan can use.

Modes

Per field, recomputed every run

Most of the tool works with no human labels at all. It is explicit about which parts don't, and how few you would need.

modeYou haveYou additionally get
0 nothing distributions, drift, judge health, relative leniency, cross-field consistency, triage ranking, fuzzy label pairs
1 ~100 labelled accuracy, macro F1, confusion matrix, tree buckets, judge direction, the operating-point table
2 ~100 double-labelled whether your taxonomy is actually crisp — and everything above becomes trustworthy

Mode is per field, so jtbd can be in Mode 1 while summary sits in Mode 0. Both appear in the report banner with what they cannot support.

Execution

Collect once, analyse for free

   COLLECT  ──► verdicts.jsonl        costs money. run once.
                        │
                        ▼
   ANALYSE  ◄────────┘                free. run a hundred times.

   cache key = (judge, model, prompt hash, item, field, output value)
Fig 5 — the only expensive operation is isolated behind a file

Change a threshold, add a check, fix a reporting bug, try a different target — analyse re-runs against the cache and issues zero model calls. Cheap reporting code that only ever runs after an expensive collection is its own failure mode; this removes it.

cli
llm-expectations run      run.yml        # collect + analyse
llm-expectations plan     run.yml        # cost estimate, no calls
llm-expectations analyse  out/<run>/     # re-analyse from cache, free
llm-expectations compare  out/a out/b    # two runs, head to head
llm-expectations check    taxonomy.yml   # static taxonomy health

Interface

Five inputs, four outputs

in
items.jsonl      the units
outputs.jsonl    what the model said
taxonomy.yml     versioned label tree
judges.yml       models, keys, panel wiring
labels.jsonl     human answers (optional)
out — one folder per run
run.json         settings, modes, gates
verdicts.jsonl   every judge call
findings.jsonl   every check result
metrics.json     aggregates + intervals
report.md        readable

Kept separate because they change on different schedules — re-run the model and outputs change while items don't; add labels later and nothing else moves. JSONL because it streams; CSV, parquet and dataframes go through swappable readers. API keys are referenced by environment-variable name, so the config file is safe to commit.
